# 指标推导 · 找指标(重新推导北极星与三层指标)

本文档是 `.bw/metrics.toml` 的人读推导过程,按 Skill `north-star-discovery`
第 8 步要求,包含:输入摘要、北极星为什么是这条(以及被拒绝的候选)、三段
拆解、滞后/引领指标的因果链、每条指标采集方案的诚实评估。

## 0. 输入摘要

- **`docs/competitive-analysis.md` 不存在**——本轮无竞品分析报告输入,北
  极星推导仅基于项目自身意图(`PROJECT.md`)与真实运行记录,不假装读过。
- **`docs/metrics-toml-format.md` 在本仓库全部历史中同样不存在**(真实核
  查:`git log --all --diff-filter=A -- docs/metrics-toml-format.md` 无任何
  提交命中)——Skill 文档称其为「`.bw/metrics.toml` 唯一契约」,但工作区
  内从未真实落过这份文件。`.bw/metrics.toml` 的结构因此只能对照 Skill 正
  文内嵌的样例(`schema_version` / `[north_star]` / `[[lagging]]` /
  `[[leading]]` / `collect = { kind, query }`)校验,已用 Python 的 `toml`
  库真实解析通过、字段与样例逐一对应,但"是否与 BW 引擎解析器完全一致"
  这一点无法核实,如实标注为**未验证**。
- **项目意图**(`PROJECT.md`):AI 热点圈信息**过多**,目标是按用户自定义
  关注面,从 HN(社区热度)+ arXiv(学术前沿)聚合、去重、过滤,生成一份
  **可读**的日报。对标 Feedly(需自己订阅、无 AI 相关性过滤)与人工编辑
  的 AI 日报 newsletter(非自动化)。
- **现行北极星**(`PROJECT.md`「北极星」段):「连续 7 天,每天都真实生成
  一份包含 ≥5 条命中关注面的摘要,无需手动修正即可读」,按
  `digests/YYYY-MM-DD.md` 真实存在且命中条目数 ≥5 逐日核验。
- **真实运行数据**:`digests/telemetry.json` 当前快照
  `{date: 2026-07-21, raw: 295, hit: 97, deduped: 97, items: 29, days: 3}`。
- **优化阶段记录**(`docs/regression.md`):HN fetch 耗时 66.02s→33.50s,
  总耗时 74.29s→46.22s,最终输出条目 111→30——「输出条目从 111 降到 30
  ——达到『日报』应有的可读体量」。
- **复盘记录**(`docs/retro.md`):关键词子串匹配的假阳性率真实抽样
  238 条仅 1 处(约 0.4%,`RAG` 命中 "average");`fetch_limit` 200→100
  的假设不成立(信息损失明显,保持 200)。
- **SLO 记录**(`docs/SLO.md`):单次生成耗时当前真实值 49.7s(手动
  `time` 测量,非自动采集);「单源不可达时,另一源仍能出日报」这条红线
  **未测**;测试 19/19(后续增至 32/32)。
- **代码证据**(`aihot/render.py:141-150` `consecutive_days`):现行北极星
  依赖的「连续天数」就是逐天检查 `<date>.md` 文件是否存在的循环,不涉及
  任何人的阅读行为。

## 1. 北极星为什么要改

### 1.1 三段拆解(供给 / 使用 / 价值)

- **供给**:每天真实生成一份 `digests/YYYY-MM-DD.md` 文件,内含 ≥5 条按
  关键词打分命中的条目。
- **使用**:用户真的打开这份文件、读了它。
- **价值**:用户因此省下了在信息过载的 AI 热点圈里手动筛选的时间,看到
  了自己关注面内、原本可能错过的真实信息。

现行北极星「连续 7 天生成包含 ≥5 条命中的摘要」——核对定义,它只检查
`digests/YYYY-MM-DD.md` 文件是否存在 + 命中字段是否 ≥5,两者都是**生成
时**由程序自己算出来的,完全落在供给段。它没有回答"有没有人打开、读完、
因此变好"这几个问题,而这几个问题恰恰是 PROJECT.md 自述的痛点("信息
**过多**")真正指向的地方——痛点在价值段,北极星却卡在供给段,答非所问。

### 1.2 自动化免疫检验

现行北极星的采集逻辑是 `aihot/render.py` 里的 `consecutive_days`:逐天检
查 `<date>.md` 是否存在。给这个项目挂一条永不失败的每日定时任务
(`python3 -m aihot.main` cron 化),只要两个真实数据源不同时故障、关键
词表不为空,这条北极星会从上线当天起**永久满分**——不需要任何人打开、
阅读、认可这份日报。这正是 Skill 文档里作为反例点名的这条北极星,而且
可以用仓库里的真实代码(`consecutive_days` 的实现)而不是猜测来确认:它
的输入只有文件系统状态,不涉及用户行为。**判定:退回重写。**

### 1.3 被拒绝的候选

- **候选 A:保留原北极星,只是把 target 从"≥5"改成别的数字**——被拒绝,
  因为问题不在阈值,在于整条指标衡量的对象(文件是否生成)从根上就是供
  给段,调阈值不能把它挪到使用/价值段。
- **候选 B:「命中条目的关键词覆盖率」或「关键词库大小」**——被拒绝,这
  类指标只衡量配置/算法的复杂度,不衡量任何人的真实获益,而且同样可以
  被"扩大关键词表"这种纯配置改动刷高,不需要真实用户行为。
- **候选 C:「digests 总生成天数」或类似的产出计数**——被拒绝,这是最直
  白的供给段虚荣指标,和现行北极星犯的是同一个错误。

### 1.4 新北极星

**「连续『真实读完且有收获』天数」**——用户当天打开当日摘要后,自行确认
「读完了,且其中至少 1 条是命中我实际关注、事前不知道的真实信息」,按此
口径逐日记录,统计连续满足的天数。

- **落在哪一段**:使用段(读完)与价值段(有收获)的交集——两者缺一都不
  算数,只生成文件、没人读,不算;读了但全是已知信息、没有新收获,也不
  算。
- **自动化免疫**:cron 任务可以让文件天天生成,但不能替用户"打这个
  勾"——这条北极星的采集环节里必须有一个真实的人做出判断,满足 Skill
  要求的自动化免疫检验。
- **对齐项目意图**:直接回应 PROJECT.md「AI 热点圈信息过多」的真实痛
  点——过多的反面不是"存在一份摘要",而是"这份摘要真的帮我省了时间、
  没有把我继续淹没"。

## 2. 滞后指标的因果链

滞后指标是北极星的分解或先行验证——用户会不会"读完且有收获",取决于摘
要本身的**体量**(读得完读不完)、**精确度**(命中的是不是真的相关)、
**可靠性**(会不会开天窗)。三条滞后指标分别对应这三个必要条件:

1. **单份日报条目数(可读体量)`≤35`**——目标值来自真实历史数据校准,不
   是拍脑袋:`docs/regression.md` 记录优化阶段把输出从 111 条砍到 30 条
   才「达到日报应有的可读体量」;`digests/telemetry.json` 当前真实值
   `items: 29`,`max_items_per_source: 15 × 2 源 = 30` 是代码里的硬 cap
   理论上限。`≤35` 在这条硬 cap 之上留了一点余量,卡的是**上限**——这里
   特别提醒自己吸取 Skill 文档点名的反例教训:现行 PROJECT.md 北极星把
   类似的"命中数"字段设成 `≥5` 下限,而真实值(`hit: 97`)常年远超 5,
   这条下限形同虚设;本条改为上限,方向对着真实痛点(太多,不是太少)。
2. **关键词误判率(人工抽样)`≤1%`**——`docs/retro.md` round #19 用真实
   抓取的 238 条数据核对,误判(假阳性)仅 1 处,约 0.4%;`1%` 在这个真
   实测得值之上留了安全边际,不是凭空定的目标。误判率直接决定"无需手
   动修正即可读"能不能成立——误判越多,用户读的时候要自己甄别真假命
   中,等于要手动修正。
3. **断源仍出日报的模拟测试通过率 `100%`**——`docs/SLO.md` 白纸黑字记录
   这条红线目前「未测」,不是"测过且不达标",是完全没有真实验证过。HN
   或 arXiv 任一源故障时如果日报因此开天窗,当天的连续天数直接断掉,这
   是北极星能否稳定达成的真实风险敞口,值得作为滞后指标追踪,推动它从
   "未测"走到"真实测过"。

## 3. 引领指标的因果链

引领指标是过程性、当下可控、驱动上面三条滞后指标的先行量:

1. **单次生成总耗时 `≤90s`**——`docs/SLO.md` 记录当前真实值 49.7s,
   `docs/regression.md` 优化后 46.22s,`≤90s` 在真实测得区间之上留出明
   显余量。耗时是纯过程性、当下工程可控的量(比如 HN fetch 策略);耗时
   越长,用户越可能拖延或跳过当天的运行,间接影响北极星的"连续天数"和
   滞后指标 1(体量控制往往和抓取范围的取舍相关,`docs/retro.md` round
   #20 就记录过 fetch_limit 200 vs 100 的真实取舍)。
2. **每周合并 PR 数 `≥1`**、**队友结算 Issue 数 `≥1`**——研发/交付节
   奏,是驱动上面三条滞后指标(体量调优、误判修复、断源韧性测试都需要
   真实代码改动落地)收敛速度的先行信号。工程活动量放在引领层是合适
   的,不会被误当成北极星。**诚实说明**:真实核查(`gh pr list`/
   `gh issue list`)显示该仓库截至本轮尚无历史合并 PR、仅 1 条 open
   issue,没有历史节奏数据可供校准,`≥1` 是起步猜测而非真实校准值,需
   要下一轮积累数据后回调。

## 4. 采集方案的诚实评估

| 指标 | `collect.kind` | 现状 |
|---|---|---|
| 北极星:连续真实读完且有收获天数 | `manual` | 没有任何埋点/连接器能判断"用户读没读、有没有收获"——这本质上需要人的主观确认,诚实标 manual,不为了显得"采得到"而编一个假查询。 |
| 滞后:单份日报条目数 | `manual` | 数值其实躺在 `digests/telemetry.json` 的 `items` 字段里,但采集器 v1(见 `docs/metrics-toml-format.md`)只真采 `github`,没有读取项目内任意文件的通道,如实标 manual,而不是虚标 `bw`。 |
| 滞后:关键词误判率(人工抽样) | `manual` | 需要人工语义判断,天然只能人工完成。 |
| 滞后:断源仍出日报的模拟测试通过率 | `manual` | 需要人工断网/mock 单源不可达来跑,SLO.md 里也说明这条要靠断网单源模拟,目前没有自动化脚本。 |
| 引领:单次生成总耗时 | `manual` | `docs/SLO.md` 自己说明这条是"每次真实测量并入账",用 `time` 命令手动测,不是自动采集。 |
| 引领:每周合并 PR 数 | `github` | 采集器 v1 **已接**——`repo:{owner}/{repo} is:pr is:merged merged:>=@{7d}` 是 `gh api search/issues` 能真取 total_count 的查询,占位符 `{owner}`/`{repo}`/`@{Nd}` 都在采集器支持范围内。 |
| 引领:队友结算 Issue 数 | `bw` | BW 自己的记账口径(`issue.settled_at within 7d`),v1 未接,如实 Unknown,不伪造观测。 |

## 5. 与现行北极星的关系

`.bw/metrics.toml` 是本项目指标定义的新正本;`PROJECT.md`「北极星」段仍
保留原文字(该文件由创建流程逐步写就,改写它超出本票范围),但本轮结论
是:**原北极星是供给段指标,已被 `.bw/metrics.toml` 里落在使用/价值段
的新北极星取代**,后续如果有票专门维护 `PROJECT.md` 的北极星段落,应参
照本文档第 1.4 节同步改写。
